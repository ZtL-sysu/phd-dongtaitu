# DCRNN fixed training-prior proposal v1

**Status: proposal only; not integrated, generated, or approved for an experiment.** The root owns the final method/fairness decision. This proposes the `fixed_training_prior` required by `edsgn/staging/dcrnn_forecast_adapter_v2.py`; it does not edit that adapter or the package.

## Constraints and inspected interface

The RP explicitly says DCRNN will use a training-period interaction prior (`inputs/rp-extracted.txt` §5.3). The staging adapter accepts a finite nonnegative `[N,N]` matrix, uses it to create the original dual random-walk supports, and persists it as a `state_dict` buffer; `_rebuild_author_supports()` reconstructs the source module's non-buffer sparse supports after checkpoint loading. See `reviews/dcrnn-staging-audit-v1.md`, `edsgn/staging/dcrnn_forecast_adapter_v2.py`, and the pinned source `sources/DCRNN_PyTorch/model/pytorch/dcrnn_cell.py` / `lib/utils.py`.

There is no `edsgn/src/edsgn/prior.py`. The package has `prior_cache.py` and `ForecastModel._prior_events_raw_step()`: both implement **window-local, replay-time** evidence from `PreparedData.window()` events. Those events are restricted to the current causal input window, with email contacts or MOOC same-user activity histories. The DCRNN prior below is a different, **fixed, training-period** support, as named in the RP. The `PreparedData` contract keeps `target()` separate from `window()` and stores global event bins, fixed node IDs, split ranges and event kind (`edsgn/src/edsgn/data.py`).

The author source computes `R(A)=D^{-1}A` with zero inverse degree for isolates and gives DCGRU the two supports `R(A)^T` and `R(A^T)^T` for `dual_random_walk` (`sources/DCRNN_PyTorch/lib/utils.py:101-108`, `model/pytorch/dcrnn_cell.py:59-65`). It also includes the undiffused input term in each graph convolution; the proposed raw adjacency therefore has **no added self loops**. Preserve this source orientation and normalization; do not row-normalize or symmetrize the artifact in a second, adapter-specific pass.

## Proposed deterministic recipe

Use the bundle's exact training split `[train_start,train_stop)` and frozen node ordering. The builder should load only the designated training bundles/trajectories and read only the training-range `events` or `values` needed below. It must not access `targets`, validation/test values or events, synthetic `oracle/`, dropout/action-feature labels, or calendar fields. It should fail if the event rows or synthetic temporal pairs cannot be bounded to that training partition. All split ranges below are local bin indices from bundle metadata.

| Dataset | Raw prior `A` before DCRNN's own dual-random-walk transform |
|---|---|
| **Email** (`N=986`, `L=28`, train `[0,562)`, feature order incoming/outgoing) | For every training-range relation record `(bin,src,dst)` with both endpoints already in the training-defined cohort, increment `A[src,dst]` by one. Preserve repeated source rows as repeated interactions. Ignore event rows outside train and self-events (`src==dst`) so the model's explicit self/input term remains the only self path. The data bundle stores only core-to-core events for the relation stream; incident noncore messages used for count targets must not create graph nodes/edges. |
| **Email episode** (`N=893`, `L=28`, train `[0,368)`) | Same construction and node-index semantics as email, applied to the selected episode's own bundle and train split only. Do not use removed-gap coordinates as graph events. This is a same-source temporal supplement, not an independent replication (`protocols/email-episode-preparation-evidence-v1.md`). |
| **MOOC** (`N=78` activity targets, `L=24`, train `[0,499)`) | Select training-range `(bin,user,activity_node)` events. Build a sparse user-by-activity **binary** incidence matrix from unique `(user,activity_node)` pairs; set `A[i,j]` and `A[j,i]` to the number of distinct training users observed with both distinct activities `i` and `j`. Exclude the diagonal. This is a static shared-user projection that matches the relation meaning of the existing within-window MOOC prior, while deduplicating repeated clicks within the same user's activity history so prolific repeat clicks do not create artificial graph weight. Keep activity node IDs in the prepared cohort; raw user tokens are grouping keys, never graph nodes. No action label or feature member is needed. |
| **Synthetic** (default `N=64`; stress bundles up to `N=256`, train trajectories seeds `0–7`) | `events` is intentionally empty and the hidden transition matrices live under `oracle/`, unavailable to the adapter. Use a train-only **lag-one association proxy**, not an oracle graph: for each ordered node pair `j→i`, pool valid lagged pairs `(x[t,j],x[t+1,i])` within each training trajectory (never across trajectory boundaries), compute Pearson correlation over pooled training pairs, and set `A[j,i]=max(0,corr)` for `j!=i`; use zero when there are fewer than two valid pairs or either side has zero variance. Use `input_mask` at both times. This is a train-fitted association prior, not an estimate claimed to recover the simulator's causal `P`; disclose that synthetic differs from event-derived real priors. |

After the raw graph is assembled, require finite, nonnegative values and exact `[N,N]` shape; coalesce duplicate edges; leave rows with no outgoing edge at zero. Let the pinned DCRNN utility form its dual random walks. Do not prune weak positive weights, add synthetic self loops, add epsilon links, drop isolates, or tune a threshold on validation. Emit diagnostics only: raw nonzeros/density, directed in/out degree summaries, isolates, row-weight range, and both resulting support nonzeros. These are artifact diagnostics, not model-selection criteria.

### Sparsity/top-k decision

No top-k cap is recommended initially. The real email relation graph is already sparse in observed event edges; the MOOC graph has only 78 activity nodes even if the projection becomes dense; synthetic stress is bounded at 256 nodes (at most 65,536 matrix entries). The DCRNN staging adapter currently stores the graph buffer densely, which is only about 3.9 MiB at `986×986` float32, while its actual supports are sparse. A degree cap would delete training evidence and introduce another tuned choice without a demonstrated resource need. If a later resource measurement establishes a material limit, stop and ask the root to freeze one training-only cap rule before any validation selection; do not silently add top-k.

## Binding and reload contract for a future builder

If the root accepts the recipe, a separate pure-CPU builder should write a new, immutable prior artifact per data bundle/config (exclusive create; identical bytes may be reused only after exact comparison). The artifact bundle should contain:

- `fixed_training_prior` float32 `[N,N]`, `node_ids` in exact model order, and a canonical JSON manifest;
- source bundle path/hash, dataset name/kind, train split bounds, method/version string, formula choice, input/event fields read, and builder-source SHA-256;
- node-ID digest, prior-array SHA-256, shape/dtype, zero-diagonal assertion, nonnegative/finite assertions, and graph diagnostics;
- a strict role declaration such as `fit_source=train_only; validation_read=false; test_read=false; oracle_read=false` (synthetic train collection files only), without copying raw event rows into the artifact.

The launch binding should hash both the prior artifact and its manifest together with the ordinary config/source/data binding. Construct DCRNN with this frozen artifact for both training and inference; the persistent prior buffer in the checkpoint is the reload authority. On checkpoint restore, verify prior hash/shape/node order against the run binding, then rely on the adapter's support rebuild; re-run one identical tiny forward to verify restored supports/predictions. A changed train bundle, split, node order, recipe, or prior digest must reject reuse rather than transparently regenerate a graph under an old checkpoint.

This artifact is a graph only; do not append graph-derived features to the `[B,L,N,F]` input, add future targets to decoder calls, or revise DCRNN's forecast head. The graph has to be generated before launch and bound in the resolved configuration and checkpoint metadata.

## Information-access and fairness decision for the root

The RP requirement gives DCRNN a static graph aggregated over the complete **training period**. By contrast, the current EDSGN prior path receives only events inside each current `L`-bin input window and evolves contacts during replay (`PreparedData.window()` and `model.py:_prior_events_raw_step`). Thus DCRNN's validation/test windows can use the entire earlier training-period relation history, whereas EDSGN's local event prior has a bounded recent view; and for DCRNN training examples, the fixed train graph can contain relation events later than that particular example's origin. This is a transductive training-only side-information convention, not a per-window causal graph.

Proposed disclosure: call this baseline `DCRNN-adapted / full-train static prior`; state explicitly that the support uses only training partition information but is not origin-local. Do not claim equal graph-history access. The accuracy comparison is therefore not an information-matched ablation; any mechanism/cost interpretation should be restricted. The root may choose an additional matched-information sensitivity (same fixed training prior available to both methods, or a DCRNN window-local support) only after freezing its scope and cost accounting. A window-local DCRNN support changes the original fixed-graph semantics, while adding the static prior to EDSGN changes its input/context contract; neither should be silently substituted for the requested core method.

## Checkable evidence and unresolved choices

- Real bundle hashes, feature definitions, node construction, event semantics, masks and split bounds are in `protocols/data-implementation-evidence.md`; email episode hashes/splits/counting are in `protocols/email-episode-preparation-evidence-v1.md`.
- The synthetic generator stores activity sequences in train trajectories and deliberately isolates `P_before`, `P_after` and switches in `oracle/`; synthetic metadata documents the train seeds and matrix generator in the processed manifest and `prepare.py`.
- The staging adapter now persists the graph buffer in `state_dict` and reconstructs dual supports on load (`edsgn/staging/dcrnn_forecast_adapter_v2.py`). The earlier `reviews/dcrnn-staging-audit-v1.md` predates this persistence fix; its remaining claim that the adapter prior is plain/unserialized should not be carried forward without rechecking the v2 source.
- No prior artifact has been constructed with this recipe, no full-sized support was checked, and no DCRNN training/validation/test run is evidenced here. The static prior recipe, synthetic association proxy, asymmetrical graph-history access, serialization/binding details, and any matched-information sensitivity remain for root review before implementation.
