# P3A validation-only calibration preparation v1

Status: preparation rules for root review; no real calibration, model run, or test access was performed. This document does not change the method or infer support for H1–H3. It applies to the existing frozen model families, datasets, and registered candidate queues.

## Frozen evidence path

1. **Bind inputs before calibration.** For each exact dataset/checkpoint/device, verify `input-binding-at-launch.json`, checkpoint/source/config hashes, node ordering, train-fitted normalization/output statistics, split boundaries, and the validation prediction archive. Prediction archives must identify every validation origin in canonical order and carry predictions, raw targets, target mask, `[trajectory_id, global_origin_index]`, feature labels/units, seed, checkpoint hash, and dataset/source binding. Recompute validation targets and masks from the bound validation source before use. Do not load or inspect test predictions, labels, metrics, or test-derived thresholds.
2. **Freeze the tolerance and candidate queue before calibration.** Epsilon comes from completed baseline validation variability plus a written application-relevance rationale, with exact value, evidence hashes, metric, feature/horizon aggregation, and split declared. Keep the preregistered candidate count at or below 12; do not widen, narrow, or rank candidates after seeing test results. The original-calendar email rule is the explicit exception: its all-zero validation is unidentifiable, so run the registered technical replay if needed, but do not claim accuracy-based epsilon selection. Use the already frozen `s00` descriptive policy and label selection `unidentifiable-all-zero-validation-targets`; do not borrow the episode regime's epsilon or calibration.
3. **Determine temporal block length using validation only.** Use the existing absolute-residual validation ACF procedure and save its full lag sequence and stopping rule. Freeze
   `block_length = max(history_length, max_forecast_horizon, validation_ACF_dependence_length)`
   in forecast-origin windows. For synthetic data, estimate/record dependence within trajectories and resample within each trajectory only. Do not allow blocks to cross trajectory boundaries. If the justified block exceeds the shortest validation trajectory, or leaves insufficient support, report calibration/inference as unavailable; do not silently cap the block. For the email all-zero regime, ACF is not informative and the accepted rule fixes the block to history length 28 for descriptive reporting only.
4. **Execute and retain the validation-only calibration.** Cost-table and candidate replays are B=1; attach the active device's own measured table before every candidate replay and use the preregistered `base_ms + Cg(ceil(N·graph_fraction)) + Cs(ceil(N·state_fraction))` envelope. Record per-candidate budget components, realized action counts, mandatory work/overrun, raw-unit validation score, elapsed full-replay time, exact policy, cost-table/device hashes, and unchanged checkpoint parameter hash. Keep candidate execution and selection separate: epsilon-feasible candidates may be selected by the registered rule; if none is feasible, use the full reference and label `no-feasible-selective-policy`. The email exception is nonselecting and remains unidentifiable.
5. **Freeze before evaluation.** Write immutable calibration JSON plus a separate freeze receipt binding checkpoint, source, split, epsilon provenance, validation archive, block length/ACF evidence, device-specific cost table, candidate queue, selected policy/status, and code hashes. Only after root accepts this record may the exact frozen policy be used on test once. Test is final reporting only and cannot revise epsilon, thresholds, policy, block length, or candidates.

## Paired reporting after the freeze

For each preregistered paired contrast, compare aligned raw-unit validation or final evaluation prediction archives with exactly matching targets, masks, origins, feature order, and split; only the split authorized by the phase may be opened. Primary forecast summaries are pooled valid-cell MAE at the requested horizon steps (H=1/3/7 for email; H=1/6/24 for MOOC), per seed first and then equal-weighted across five model seeds. Also report pooled RMSE from pooled squared-error sums/counts; retain feature-specific and each-horizon counts so sparse/zero support cannot disappear in a pooled number. Keep an all-horizon pooled descriptive metric distinct from requested-horizon primary results.

Use 2,000 paired moving-block bootstrap replicates with seed 1234. Generate one shared temporal draw schedule for every method/condition in a paired contrast (and reuse the same schedule across the preregistered contrasts in a multiplicity family where the rows are aligned). Each draw samples contiguous blocks of validation origins within each trajectory and applies the same sampled origins to all five seeds and both sides of the contrast. Aggregate nodes/features inside an origin; they are not independent bootstrap units. Report the paired point estimate, percentile 95% interval, centered two-sided bootstrap p value, each seed's paired difference and five-seed mean/spread separately. Use paired raw pooled metrics; do not bootstrap unpaired method rows or treat seed copies/nodes/features as independent samples.

Apply Holm step-down correction across the complete, preregistered primary contrast family, naming the family and its full contrast count. Secondary per-horizon/per-feature diagnostics remain explicitly secondary and do not replace the primary family. Do not use favorable unadjusted secondary results to upgrade a failed primary conclusion. Negative or inconclusive outcomes are valid results; this procedure is not a positive-result gate.

It preserves the candidate queue, parameter-hash check, full-reference fallback when no candidate meets epsilon, and the explicit all-zero email status/fixed `s00` behavior. `protocols/calibration-cost-budget-implementation-v1.md` records the focused 9-test evidence; this is code evidence, not actual P3A calibration evidence. `calibration-budget-audit-v1.md` documents the preceding mismatch; the implementation repair addresses its cost-envelope and fallback concerns.

`statistics.py` already checks five prediction files per side, exact target/mask/origin alignment, raw-unit arrays, paired left-minus-right differences, trajectory-bounded circular blocks, pooled RMSE sufficient statistics, and Holm within named families. Existing evidence is `protocols/statistical-implementation-evidence.md` (10 CPU tests). It does **not** determine/freeze the block length; that remains a validation-only input. Its current `run_config` uses `seed + contrast_index`, so it does not guarantee a byte-identical shared draw schedule across multiple contrast rows. Before using it for the requested shared-family draws, either provide shared precomputed indices to all aligned contrasts or record a small tested implementation repair; merely repeating seed 1234 is insufficient when the runner offsets the seed. Likewise, calibration's ACF helper must be checked against canonical sorted origin order and the max(history, horizon, ACF) rule when the actual validation archive is available. These are P3A acceptance checks, not claims that the current code already fulfills them.

Main email validation is confirmed by the existing preliminary numeric audit to contain zero valid target values in both features for all 74 validation origins; the observed zeros are not missing values. Predictive quality and substantive epsilon selection are therefore unidentified there. Report zero support and the fixed nonselecting policy transparently; a zero score is not evidence of forecasting ability. The separately split email-episode data can support only its own within-source diagnostic and cannot repair main-email identifiability.
