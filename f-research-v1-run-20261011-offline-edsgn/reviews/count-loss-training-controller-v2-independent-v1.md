# Count-loss controller v2 — independent engineering review

**Verdict: revise before any launch.** The isolated queue validation and mocked child path are substantially aligned with the design, but the controller narrows the existing owned-process barrier and can miss another active baseline, bound training, or resource-probe process.

`_private_bound_controller` replaces the unchanged runner’s `_is_training_process` with `lambda: bool(_owned_processes(root))`. The replacement scanner recognizes only `count_loss_training_controller_v2.py` and `count_loss_training_adapter_v1.py`; the unchanged bound runner recognizes `baseline_campaign.py`, `bound_phase_campaign.py`, `frozen_robustness_phase.py`, `profile_training_forward_components.py`, resource-probe scripts, and its model-training module forms. Thus the count-loss launch can proceed while a different owned training/resource job is active. This directly conflicts with the root design’s “reject other owned model/training/resource processes” requirement and its instruction to extend process detection without dropping existing coverage. `_owned_processes` also treats `psutil.AccessDenied` as ignorable, so it is not fail-closed when an owned Python process cannot be inspected. These are launch-barrier gaps; the existing tests do not cover them.

Other reviewed paths are coherent at source level. `validate_queue` pins the exact email/MOOC V4 seed-0 configs, candidate-selection helper output, actual numeric-v3 and root-acceptance evidence, and passes the canonical pre-P4 validator; the numeric-v3 schema really does contain `dataset_path` (the test JSON’s human-readable `actual_numeric_schema_checked.dataset_path` note incorrectly says otherwise). The private function-global copy of the unchanged bound runner installs the exact adapter command, rechecks pinned bytes, gates each child on the aggregate 72-hour budget, and checks both child argv and active-process state. The wrapper’s resource lease release is ownership-checked; tests show the campaign/resource leases are removed after successful mocked children and a refusal before child launch. Existing nonempty outputs are rejected, and the runner does not resume or retry failed scientific jobs.

The focused CPU tests passed **5/5** in the fresh local Conda run (29.77 s). They use temporary metadata and mocked validators/children; they do not authorize a real run.
