# AGCRN recurrent-activation memory diagnosis

This is a read-only source analysis. I did not run the model, load data, use CUDA, or launch an optimizer. The observed resource result supplied by the owner is that the external queue passed synGW/AGCRN/STAEformer/DCRNN at B64 and emailGW at B2, while emailAGCRN at B2 OOMed after reaching 8.57 GiB allocated against an 8.79 GiB allowance. B1 had not yet been measured at audit time.

The likely AGCRN-specific cost is repeated expansion of node-adaptive weights and graph supports inside every recurrent step. With the adapter defaults (`hidden_dim=64`, `num_layers=2`, `cheb_k=2`; `rp_forecast_adapters_v2.py:202-220`) and N=986, L=28, the upstream encoder invokes 56 recurrent cells (`AGCRN.py:24-31`); each cell runs both a gate AVWGCN and an update AVWGCN (`AGCRNCell.py:10-22`), for 112 AVWGCN calls. Each AVWGCN materializes node-specific weights of shape `[N,K,dim_in,dim_out]` via einsum (`AGCN.py:21`) and uses them in the final einsum (`AGCN.py:25`).

Assuming F=1 and float32, one cell step's gate plus update expanded weights are approximately `N*K*(F+64)*(128+64)*4` bytes, or 98.4 MB. If autograd retains these per-call operands for backward, 56 steps account for about 5.51 GB decimal (5.14 GiB) of expanded-weight tensors alone. This is an estimate, not a measured live allocation; the exact saved tensors depend on PyTorch's contraction/autograd kernels. B2 doubles batch-dependent intermediates such as `x_g`, but does not double those node-specific weights, since they are independent of B.

Dense supports add another likely retention source. Every AVWGCN call independently computes `[N,N]` similarities, softmax supports, and a `[K,N,N]` support stack (`AGCN.py:14-23`). At N=986, each K=2 stack is about 7.78 MB decimal; 112 separately-built stacks would be about 871 MB if retained. The similarity/ReLU/softmax intermediates can add more. These repeated dense calculations and expanded weights explain why lowering B may help only partially; the repeated unrolled encoder graph is the stronger structural suspect.

If B1 still OOMs, the lowest-risk exact-family remedy is **training-only activation checkpointing around each official `AGCRNCell` call in the adapter**. Preserve the official nested layer/time order and same initial states, inputs, cell modules, embeddings, stacking, final convolution, and raw forecast transform. In grad-enabled training, call `torch.utils.checkpoint.checkpoint(cell, x_t, state, node_embeddings, use_reentrant=False, preserve_rng_state=True)`; retain ordinary `self.network(values, targets=None, teacher_forcing_ratio=0.0)` exactly for evaluation/no-grad. Passing `node_embeddings` explicitly keeps its gradient in the checkpointed call; `use_reentrant=False` also supports first-layer `x_t` that does not itself require gradients. Checkpointing should discard the inner AVWGCN expanded-weight/support activations between steps and recompute them in backward. It increases backward compute and does not change cell equations, candidate graph, hidden width, history, or layer count.

Current upstream AGCRNCell/AVWGCN contain no dropout, batch normalization, in-place state mutation, or random operation. Thus recomputation should be deterministic for the present implementation. Keep `preserve_rng_state=True` for future stochastic operations. BatchNorm would be a hazard because recomputation would update running statistics twice; if introduced upstream, checkpoint only after explicitly preserving single-update semantics or keep it outside the checkpointed function. Dropout requires RNG preservation and parity tests.

Before adopting the change, run a CPU toy parity test on the official model with B=2, N=5 or 7, F=2, L=4-6, H=3, two layers and K=2 using identical seeded weights and inputs. Compare forward outputs, graph/head outputs, input gradients, node-embedding gradients, and every parameter gradient between ordinary and checkpointed training paths; require finite gradients and tight float32 equality (`rtol=1e-6`, `atol=1e-7` or stricter if bitwise equal). Also verify eval and no-grad never invoke checkpointing and match the unmodified official call. Only after this CPU parity should the owner measure B1/B2 GPU peak memory under the existing queue ceiling; do not infer a memory or speed win without that run.
