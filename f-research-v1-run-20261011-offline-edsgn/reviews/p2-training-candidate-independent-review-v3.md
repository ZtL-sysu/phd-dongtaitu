# Independent review: opt-in tensor candidate path (v3)

**Disposition: no blocker found against the audited proposal; narrow engineering parity only.** Read-only review of package source, probe receipt, prior v3 probe audit and saved CPU test evidence. No test was rerun and no data/model/GPU/optimizer was used in this review.

`ForecastModel._candidates` switches to `candidate_batch` only when `training_candidate_tensor=True`, the model is in training mode, gradients are enabled, runtime contacts are nonempty, variant is not V0, and K is positive. Config default is false. Evaluation, inference, no-grad, V0, missing-contact, and K=0 paths remain on the reference implementation. Proposal changes the candidate/contact merge backend only; it does not alter model parameters, graph scorer, candidate source, scheduling, or forecast equations.

The helper matches the reference ordering: each row's contact dictionary is sorted by descending frequency then ascending node ID and truncated to K; bounded exploration candidates already exclude self; contacts take priority, duplicate exploration candidates are masked, the valid merged list is truncated to K, then candidate IDs are sorted for deterministic downstream ordering. Contact counts follow retained contacts and are zero for exploration-only candidates. Work is bounded by the `[B*N,K]` contact pack and `[selected_rows,K,K]` membership comparison, with no dense N-by-N candidate matrix. This relies on model runtime contacts already being capped at K, as confirmed in `_prior_events_raw_step`.
