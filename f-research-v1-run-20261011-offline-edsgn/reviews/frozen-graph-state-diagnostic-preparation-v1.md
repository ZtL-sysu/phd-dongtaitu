# Frozen graph/state diagnostic preparation review

The independent staging runner is at `edsgn/staging/frozen_graph_state_diagnostic_v1.py`. It follows the existing evaluation gate (`P3A=passed`, `P4=running`), verifies the checkpoint/policy through `engine.validate_freeze`, binds the complete trajectory+oracle byte collection and both trace/diagnostic source hashes, requires every test origin, and rechecks weights and collection hashes after inference. Its CLI acquires both managed resource leases, checks the owned-process scan and cumulative 72-hour budget before the run and at every origin. There is no limit/smoke option.

The model is called with only its causal test windows, event records, selected policy, and normal training-derived frozen normalization. Oracle NPZs are opened only after all predictions are produced, the freeze is revalidated, and the entire frozen collection fingerprint is rechecked. The post-inference oracle block computes a retained-time transition matrix and raw directed-support overlap counts; it never calls model or scheduler code. This stays within the plan's restricted synthetic-structure diagnostic and does not treat predictive accuracy as causal-edge identification.

The gzip trace records actual graph/state row IDs, model `c`, pending-log retention before/after state update, `exp(pending_log_g)` at consumed rows, membrane and pending-spike snapshots around clock decay and state update, input/effective graph/state age, graph/state decisions, and per-origin counters. Row TV is computed on support-ID-aligned dense rows and is null for an uninitialized graph. Predictions and raw targets are retained with each origin's signed distance from the oracle switch; horizon metrics are also reported. No arbitrary recovery bins or pass threshold are added because the inspected plan requires a recovery curve but does not define a scalar recovery estimator.

Retention attribution remains bounded. `refresh_graph` runs before the current step's state update, so a same-step graph can match under identical checkpoint, runtime, inputs, and policy. Changed retention affects the updated state and readout; the next step's prediction-residual monitor and adaptive scheduler/scorer can then change later graph rows or refresh counts. The runner reports each arm's realized graph rows and counters but does not claim whole-window graph equivalence across shuffled-c, constant-g, or reset interventions. An isolated retention effect would require a matched counterfactual that replays identical graph rows/actions from the same checkpoint and input stream while changing only the retention signal; that is a distinct controlled analysis and is not implemented here.

CPU-only toy checks passed (5/5), including a passive-hook parity check for predictions, graph loss, and final membrane state, support-aligned TV, abrupt/gradual oracle timeline interpolation, collection fingerprint changes, and fail-closed stage/resource guards. No real test collection, checkpoint, GPU, optimizer, or test replay was accessed. The current ledger is P3 running, P3A pending, P4 pending, so actual replay remains blocked. This is preparation evidence only, not a P3A/P4/P5 result.
