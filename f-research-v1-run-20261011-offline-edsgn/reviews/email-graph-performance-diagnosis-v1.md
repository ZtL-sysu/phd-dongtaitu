# Email V1 graph-path performance diagnosis (read-only)

**Conclusion.** The warm replay has an unusually large host-side `graph_ms` (16,471.06 ms across the traced eight-window pass), but this is not measured GPU elapsed time. The strongest concrete avoidable work inside that timed section is `_candidates()` repeatedly transferring candidate IDs to CPU and sorting Python contact maps row-by-row. The timing data cannot establish how much of the 16.47 s this explains; graph scorer/ranking work is also inside the same region.

## Evidence

- `logs/email-training-component-resource-v1.json` labels component times as CUDA host enqueue/submission diagnostics, explicitly says not to sum them as device elapsed time, and marks the traced pass as including trace overhead. The pass-3 synchronized whole forward+backward was 20.341 s; the least-instrumented warm pass-2 was 21.868 s. Pass 1 was cold (31.280 s). All three had the same loss (6.23618), finite predictions/gradients, and identical before/after weights. These are functionality/resource diagnostics, not scientific timing claims.
- The log records `model.py` SHA-256 `b60c7e3c4c961ed87ba9b4d9fac604f63f7c9b2aef351bba18741921f6b97d9c`; current file hash matches.
- `forward()` times `refresh_graph()` as `graph_ms` at `model.py:519–520`. This region includes candidate construction, scorer, stable top-k, aligned-TV and graph bookkeeping. `candidate_ms` at `517–518` measures `_prior_events()`, not `_candidates()`.
- In `_candidates()` (`model.py:335–365`), when contact priors exist, every refresh does `candidates.cpu().tolist()` and `ids.cpu().tolist()` (`351`), then for every row looks up Python dictionaries, sorts contacts by `(-frequency,node_id)` (`353–360`), creates new GPU tensors (`361–362`), and stable-sorts candidate IDs (`363–365`). On CUDA this forces device-to-host synchronization and round-trips the candidate matrix. With full-policy B8 and N=986, up to 7,888 rows are handled per refresh; the graph path is invoked through the sequence. Candidate host timer’s 646 ms does **not** include this section.
- `refresh_graph()` scores every candidate (`model.py:380–397`; V1 scorer at `387–396`) and applies stable descending argsort over each candidate row (`398`) to preserve deterministic equal-score ordering. The candidate rows are sorted by node ID first, so stable score ordering gives the lower node ID tie priority. Replacing this with ordinary `topk` would not guarantee parity.
- `aligned_change()` (`model.py:33–42`) computes overlap by pairwise ID equality and minimum weight. It is explicitly bounded to the old/new supports `[rows,k,k]`, not an N×N graph. For configured `k=8`, this is at most 64 comparisons per refreshed row; it is not an obvious dense all-node bottleneck. Keep its union/empty-support semantics and autograd through weights intact.

## Exact-parity optimization candidates

1. **Remove repeated contact sorting first.** Maintain each node’s contact-priority list in `runtime` and update/invalidate it exactly when that node’s contact counts change in `_prior_events()`. The priority key must remain `(-count,node_id)`; candidate merge must still take the first K contacts and then fill from that row’s exploration pool excluding every contacted node. This can remove one Python sort per refreshed row. Validate against the current implementation on tie counts, >K contacts, zero contacts, changing counts, and partial row IDs.
2. **Avoid the candidate CUDA→CPU→CUDA round trip.** Contact dictionaries are CPU-owned, so a CPU candidate representation/mirror is a plausible exact route. Keep its phase/exploration-pool updates and selected row IDs synchronized with the existing deterministic formulas, then return only the merged `[rows,K]` IDs/frequencies. Alternatively retain a compact CPU mirror of candidate pools. Do not assume the sync disappears if IDs are still copied from CUDA; test actual synchronization behavior. Compare exact candidates and frequencies for full and partial/adaptive row sets, across phase transitions and N=1.
3. **Keep ranking deterministic.** The stable ID ordering followed by stable descending score argsort encodes tie behavior. Any fused/partial top-k replacement must reproduce lexicographic `(-score,node_id)` selection and preserve gradients for gathered selected scores. `topk` alone is not an exact substitute.
4. **Do not optimize aligned-TV by dropping the pairwise union.** Its bounded support comparison directly implements the required aligned total variation. A lookup-based replacement is possible only after proving uniqueness/padding assumptions for old and new supports and checking empty/uninitialized cases, plus matching gradients exactly.

## Limits / uncertainties

No profiler operator trace was collected (`top_operators_pass3` is empty), and the available per-component CUDA numbers are host timing. Thus the diagnosis identifies avoidable synchronization/Python work in the measured graph region but cannot apportion its time or distinguish Python dispatch from GPU queueing. The scorer processes roughly `B*N*candidate_cap = 252,416` candidate rows per full refresh before top-k; its batched MLP and stable ranking may also be material. Any optimization should be assessed by exact output/runtime/counter/loss/gradient parity and a separately synchronized whole-window benchmark under controlled resource conditions.
