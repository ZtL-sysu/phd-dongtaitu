# Robustness event-channel scope audit v1

## Finding

The current missingness implementation is a **feature-channel outage with historical relation-event metadata retained**. It is not, by itself, an event-log outage. That distinction is explicit in the accepted recipe protocol (`protocols/robustness-recipes.md:3,7-15`): it defines “causal input-only perturbations”; masks are generated over `[T,N,F]`; `event_time_jitter_bins` is a separate optional intervention on event-prior timestamps; and the window returns both masked inputs and within-window events. Therefore the code path is not inherently future leakage or a violation of the currently documented input-only recipe.

The requested sources do not establish that every count-feature mask must also mask the event prior. They do establish that the model may use causal past interactions as a distinct relation prior. However, if a result is described as robustness to **incomplete source event records / a joint record-feed outage**, the present recipes do not test that condition: raw events used to derive counts remain available to the prior. Use a narrow label unless root explicitly adds a joint outage condition.

## Evidence and exact behavior

- RP original text, `inputs/rp-extracted.txt:104-110`: incomplete event records can resemble behavior changes; a zero event count in a fully observed interval differs from an unavailable record; robustness will simulate missing time blocks and incomplete groups of entity histories “without treating every absent interaction as missing data.” This establishes missingness as an important threat and distinguishes unavailable records from zero, but does not state that every feature-mask mechanism must remove relation-prior events jointly.
- RP `inputs/rp-extracted.txt:152-160`: the origin information set can include records, metadata, and an optional relation prior, provided they are available at the forecast origin; future interactions are excluded. RP `:169-185, :191-199` defines historical contact candidates/interaction frequency as a separate prior and scoring input, with only past edges allowed. RP `:477-481` requires zero counts only for fully observed intervals and masks for unavailable inputs; it does not give a joint mask-to-edge rule.
- Detailed implementation plan `博士RP_离线三模块详细实施方案.md:55-70, 93, 100-104`: separate `input_mask` from `target_mask`; robustness may mask inputs while retaining original targets; zero event counts and unavailable records differ; candidates/priors must be available at each origin. `:187-210, 226` uses history interaction frequency as a scoring input alongside masks/ages and says missing input must not create residuals. No clause explicitly couples `input_mask` to `events` visibility.
- Frozen recipe `protocols/robustness-recipes.md:7-15`: `random` masks `[T,N,F]`; `time_block` masks bins across features/nodes; `related_group` masks activity nodes across the full trajectory. Event-time jitter is independently specified and only changes event timestamps, not count features (`:13`). The text explicitly promises windows containing both input mask/values/ages and within-window events (`:15`).
- Implementation `edsgn/src/edsgn/robustness.py:168-191`: the three missingness recipes alter `visibility` and `effective_mask = original_mask & visibility`; no event rows are removed here. `:211-216` copies all base events and optionally jitters timestamps. `:240-284` returns masked `values`, `raw_observations`, `input_mask`, recalculated age, **and** event records. Without jitter, event rows are filtered only to `[window_start, origin]` (`:271-273`), independent of the missingness mask. Targets delegate unchanged to the base object (protocol `:15`; wrapper behavior is read-only).
- Causal model path `edsgn/src/edsgn/model.py:297-334`: at each step it selects records matching the current historical bin, converts MOOC user-target events into bounded user-history co-occurrence contacts, or email events into contacts, then updates the contact prior. `:335-365` merges those contacts into the candidate pool/frequencies. `:500-520, 547-560` calls prior processing for each step in the window. This establishes a genuine metadata side channel when feature masks hide counts, but the events remain bounded to the supplied causal window and are not future targets.
- Data contract `edsgn/src/edsgn/data.py:115-165`: ordinary windows similarly return records in the history window through origin, separately from masked values. No code here says a feature outage invalidates events.

## Scope decision for root

1. **Keep the current recipe meaning (minimal, consistent with its frozen wording):** label/report these as `activity-feature/history missingness; causal relation-event metadata retained`. This tests whether graph/state logic remains robust when measurement features are unavailable but the event-prior channel remains observable. Report event-prior availability as an explicit condition; do not call it complete event-log missingness. No code correction is indicated for that stated estimand.
2. **If the required estimand is incomplete event-log or shared-feed outage:** add a separately frozen joint-channel recipe/condition. The outage mapping must explicitly define which event rows are removed for a time block or unavailable entity/group, then filter rows before the model's causal prior path; preserve clean targets/masks and the same perturbation across methods. Keep current feature-only recipes as a distinct control. Do not silently alter their established digest/semantics.
3. A separate event-only outage control could isolate reliance on the relation prior, but neither the named robustness protocol nor the cited plan text explicitly requires that extra cell.

This audit does not decide which estimand is required. The source wording supports the current feature-only recipe, while the RP motivation also makes a joint source-feed outage scientifically relevant if such a claim is planned. The minimum change is a scope label; implementing joint masking requires root to freeze that added condition first.
