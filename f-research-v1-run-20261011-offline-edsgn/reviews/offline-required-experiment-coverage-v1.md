# Required P3–P5A experiment coverage extraction

This extraction translates the immutable offline plan and accepted P1B constraints into evidence-checkable rows in `protocols/offline-required-experiment-coverage-v1.json`. It distinguishes an experiment requirement from code/data preparation and from a resource probe. Existing pipeline state has P3 running and P3A/P4/P5/P5A pending; no test metrics were opened for this extraction.

The hard coverage is: baseline reproduction on synthetic, email, and MOOC; development queues before P3A; then matched V0–V9 mechanism controls, five formal model seeds for the selected core contrasts, H1/H2/H2A/H3 evidence, synthetic boundary/scaling scenarios, paired frozen robustness recipes with clean targets, temporal block-bootstrap inference and Holm correction, and actual CPU plus CUDA B1 float32 frozen profiles with ten warmup windows and five repeats. The accepted email-episode bundle is an additional within-source regime and does not replace the original email calendar. Full completion includes per-horizon raw-unit errors, activity strata, transition/recovery slices, measured compute costs and the five declared figures; null and failed findings must remain visible.

P3 queues are currently seed-0 development train/validation only. The P4 queue covers V3/V4/V2/V9 pilots; V5/V6/V7 share V4 frozen weights, and V8 uses V2. Those artifacts do not cover formal five-seed final results, robustness evaluations, complete timing, or P5/P5A review. Source routes and one-batch resource passes are not full training evidence.

Budget evidence is thin for a reliable point forecast. The last reconciled aggregate snapshot is stale (before later P3/P4 work). Six completed optimizer runs range from 187 seconds to 2,324.5 seconds, with synthetic V1 at 55.35 seconds per epoch the slowest observed average. If six trainable variants (V0/V1/V2/V3/V4/V9) each need five seeds across three primary datasets, applying that slowest observed epoch rate to 100 epochs yields a transparent planning scenario of about 138.4 hours, before external baselines, robustness, calibration and CPU/CUDA profiles. This is not a forecast that unrun models share V1’s rate; it shows the 72-hour cap is at risk and the current remaining budget cannot be stated from the stale snapshot.

Two scope ambiguities are surfaced rather than decided: the RP also discusses later trade/recommendation/ranking applications, while the authorized M0–M6 execution contract is synthetic/email/MOOC; and the RP describes a streaming protocol while this version’s plan selects independent-window evaluation. These are outside the current required queue unless scope is formally changed. The exact bounded count-noise magnitude also needs validation-time preregistration before robustness runs.

One protocol check needs root interpretation before treating the P4 queue as cap-compliant: the current queue contains 16 jobs (four variants × four dataset regimes), while the execution contract caps pilots at 12 per new module. Whether the cap is applied to each dataset row, unique mechanism/configuration, or the supplemental episode rows is not resolved by the inspected documents. This extraction flags the ambiguity without changing the queue.
