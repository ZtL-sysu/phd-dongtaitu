## Bridge evidence and blockers

The existing writer tests pass (10 passed). My four additional CPU checks pass and expose these behaviors:

1. **Prediction bytes are not tied to the engine manifest before completion.** In a real toy `engine.evaluate_run` path, I altered `predictions.npz` immediately after the engine returned while keeping its shape and origins valid. The bridge returned successfully and wrote a `completed` receipt containing the altered file's new hash. The engine manifest has no prediction-archive checksum, and the bridge checks only origins and first-axis lengths before enumerating output hashes. A completed artifact therefore need not be the forecast actually produced by the frozen engine call. Bind/hash the exact prediction, target, mask and origin payload at production and reverify it at finalization, or compare every serialized array byte/value against the returned in-memory result before completion.

2. **Failure receipts underreport test access.** A CPU toy engine run completed its test evaluation, then my test mutated the accepted helper record before the bridge's final input fence. The bridge correctly failed and released both locks, but the failed receipt still recorded `test_accessed: false`; this field is set true only in the final success update. Set the field conservatively before entering the test evaluation path (or on the first test batch), and keep it true through later exceptions.

3. **Acceptance semantics are only partially validated.** The actual root acceptance record has `scientific_hypothesis_accepted=false`, `pipeline_advanced=false`, and `c07_experiment_closed=false`. `_validate_blind_acceptance` checks `accepted_by`, `verdict`, `scope`, and all evidence hashes, but does not require these non-scientific status flags. My CPU fixture changed all three to true while retaining the accepted helper hash and the bridge's validator accepted the record. Require the exact engineering-only false flags (and `actual_blind_control_run=false`) before prediction; runtime before/after hashing alone only proves that the changed file stayed unchanged during that run.

The bridge otherwise has useful safeguards: exact policy `asdict` and digest matching against the freeze; manifest equality for checkpoint, parameters, source snapshot and policy; P3A/P4 canonical gate/hash fences; at-launch binding verification; train-statistic normalization checks and node/horizon/task alignment; complete ordered origin checks; FP32/B1 execution; and lease cleanup on both success and the tested failure. The final live-budget callback is invoked immediately before setting `status=completed`, and the injected last-check budget failure leaves a failed receipt. The `finally` block then updates elapsed time and writes the receipt without another budget callback, leaving a narrow finalization-time stop-loss boundary worth closing for a strict hard cap.

Validation evidence: existing writer suite **10 passed**; independently designed registry and CPU mutation suite **4 passed**. The mutation tests are evidence of the three listed gaps, not acceptance evidence for the bridge. No actual production prediction or scientific endpoint has run.
