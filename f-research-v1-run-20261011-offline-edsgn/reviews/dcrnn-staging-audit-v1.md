# DCRNN staging adapter audit v1

This is an unregistered local staging adapter, not an integrated baseline and not an experiment result. It targets the pinned `sources/DCRNN_PyTorch` snapshot at commit `d92490b808ba5c5be2f23d427d96e9a56b066d7f`. The upstream README identifies the DCRNN paper (Li et al., ICLR 2018; arXiv:1707.01926) and links the PyTorch implementation; the snapshot includes an MIT license. SHA-256 values for the untouched cell, model, utility, YAML, README, and license files are recorded before/after the CPU smoke in `logs/dcrnn-staging-smoke-v1.json`; they match.

`DCRNNForecast` retains the upstream `DCGRUCell`, two-layer encoder, autoregressive decoder, dual random walks, diffusion order 2, and defaults of 64 recurrent units and curriculum learning disabled. Its forward adapter only reshapes `[B,L,N,F]` to the author's `[L,B,N*F]`, zero-fills masked values, and maps `[H,B,N*F]` back to `[B,H,N,F]`; counts use the shared `softplus(logit) * output_scale` transform. Mask, age, raw, policy, and event priors are accepted by the common API but are not additional DCRNN quality/event channels. Decoder teacher labels are never supplied.

Import accommodation is isolated to temporary `lib`/`model.pytorch` namespaces. The author `lib/utils.py` imports TensorFlow at module import, so the adapter extracts and compiles the exact AST of `calculate_random_walk_matrix` with its original NumPy/SciPy operations and supplies only that function to the source cell module. It does not import the TensorFlow-dependent data/trainer utilities or alter the random-walk formula. The source's global auto-CUDA device is set to CPU during initialization; adapter `_apply` moves the non-buffer sparse supports alongside parameters and updates isolated source globals to the resulting device.

Upstream `LayerParams` registers gate/convolution parameters on first forward. The constructor performs a no-grad dummy encoder/decoder pass before returning, then verifies a second dummy pass creates no parameters. This stabilizes optimizer/state-dict parameter sets. `_supports` are plain attributes and are not in `state_dict`; checkpoint reconstruction must use the exact same frozen training-derived prior. The constructor therefore requires an explicit finite nonnegative `[N,N]` `fixed_training_prior`, but this task did not implement or validate its real-data construction, provenance filtering, or anti-leakage fit. It must be generated from training information only by the integration owner.

CPU toy checks used only an artificial 5-node ring prior and random inputs: `(L,H,F)=(24,24,1)` and `(28,7,2)`. Both returned finite expected shapes; every parameter had a finite gradient; counts stayed at 371,393 and 373,378 respectively after the real forward; CPU support migration passed; and a re-instantiated module loaded with the same prior/state reproduced predictions within absolute tolerance `1e-7`. No optimizer, real dataset, labels, GPU, or test predictions were used. The measured process wall time is a smoke-run measurement only, not a scientific speed claim.

Remaining integration checks: validate training-only prior construction and serialized prior identity, ensure the evaluation checkpoint path reconstructs the adapter with that prior, and compare its common API against the exact package/engine protocol before registration. No claim about forecast quality, computational efficiency, or scientific validity is made here.
